# 3. Architecture — What Each File Does and Why

This doc walks through the codebase file by file, explaining the decisions behind the structure. Read this alongside the actual code.

---

## The Layer Cake

```
Request → Router → Controller → Model/DB
                               → External API (OpenAI, Google)
         ↑ Response (schemas define shape)
```

| Layer | Responsibility | Example |
|-------|---------------|---------|
| **Router** | HTTP concerns only — parse request, call controller, return response | `routers/auth.py` |
| **Controller** | Business logic — what to do, not how to handle HTTP | `controllers/auth_controller.py` |
| **Model** | Database schema — source of truth for what's stored | `models/user.py` |
| **Schema** | API contract — what the client sends/receives | `schemas/chat.py` |
| **Core** | Shared utilities — config, DB engine, security, OAuth client | `core/security.py` |

### Why controllers?

Routers should be thin. If you put business logic in routers, you end up with 200-line route functions that are impossible to test. Controllers let you:
- Test business logic without HTTP (just call the function)
- Reuse logic across routes (e.g., `issue_tokens()` is used in both login and refresh)
- Swap the HTTP layer (e.g., add WebSocket support) without touching logic

## Core — The Foundation

### `core/config.py`

Uses **Pydantic Settings** to load all config from environment variables. Every setting has a type and a default. The `.env` file is the local override.

```python
class Settings(BaseSettings):
    GOOGLE_CLIENT_ID: str = ""
    JWT_SECRET_KEY: str = "change-me"
    # etc.
    
    model_config = SettingsConfigDict(env_file=".env")
```

**Why Pydantic Settings?** It validates types at startup. If `ACCESS_TOKEN_EXPIRE_MINUTES` is set to `"banana"`, the app crashes immediately with a clear error instead of failing at runtime when it tries to do math with a string.

### `core/database.py`

Creates the async SQLAlchemy engine and session factory. The `get_db()` dependency handles the session lifecycle:

```python
async def get_db():
    async with async_session() as session:
        yield session          # route uses it
        await session.commit() # auto-commit if no error
```

**Why auto-commit?** It removes boilerplate. Without it, every route needs `await db.commit()` at the end, and forgetting it = silent data loss.

### `core/security.py`

Three jobs:
1. **Create JWTs** — `create_access_token(user_id)` → signed JWT string
2. **Verify JWTs** — `verify_access_token(token)` → payload dict or 401
3. **Create refresh tokens** — `create_refresh_token(user_id, db)` → raw token (cookie), hash (DB)

**Refresh token hashing:** The database stores `sha256(token)`, not the raw token. If the DB leaks, the attacker gets useless hashes. The raw token only lives in the user's cookie.

```python
def hash_token(raw_token: str) -> str:
    return hashlib.sha256(raw_token.encode()).hexdigest()
```

### `core/oauth.py`

Registers the Google OAuth client using **authlib**. The key line:

```python
oauth.register("google", server_metadata_url="https://accounts.google.com/.well-known/openid-configuration")
```

This tells authlib to discover Google's endpoints automatically (auth URL, token URL, JWKS for signature verification). You never hardcode Google URLs.

## Models — The Database Schema

### `models/base.py`

Every model inherits from `Base`, which gives you `id` (UUID), `created_at`, and `updated_at` for free. UUIDs are used instead of auto-incrementing integers because:
- They're globally unique (safe for distributed systems)
- They don't leak information about how many records exist
- They're generated by the app, not the DB (no round-trip needed)

### `models/user.py`

```python
class User(Base):
    email: Mapped[str]           # unique
    username: Mapped[str]        # unique, derived from email
    hashed_password: Mapped[Optional[str]]  # nullable — OAuth users don't have one
    is_active: Mapped[bool]
```

**Why is `hashed_password` nullable?** A user who signs in via Google never sets a password. Making it nullable means you can have OAuth-only users and password users in the same table. The `is_active` flag lets you soft-delete users without losing their data.

### `models/oauth_account.py`

Links a user to their external identity providers:

```python
class OAuthAccount(Base):
    user_id: FK → users
    provider: str         # "google", "github", etc.
    provider_user_id: str # Google's `sub` claim
    provider_email: str
    
    __table_args__ = (UniqueConstraint("provider", "provider_user_id"),)
```

**One user, many providers.** A single user can have rows for Google, GitHub, etc. The unique constraint ensures no duplicate links.

### `models/chat.py`

Two tables: `conversations` (belongs to a user) and `messages` (belongs to a conversation):

```
User → has many → Conversations → has many → Messages
```

Messages store `role` ("user" or "assistant") and `content`. The order is determined by `created_at`.

### `models/refresh_token.py`

```python
class RefreshToken(Base):
    user_id: FK → users
    token_hash: str      # sha256 of the raw token
    expires_at: datetime
    is_revoked: bool
```

**Why a separate table?** Refresh tokens need to be revocable (logout, theft detection). Storing them in a table lets you query/revoke them. The `token_hash` column means even a DB leak doesn't expose usable tokens.

## Controllers — The Business Logic

### `controllers/auth_controller.py`

The core auth flows:

| Function | What it does |
|----------|-------------|
| `handle_oauth_callback()` | Account linking — find existing user or create new one |
| `issue_tokens()` | Create access JWT + refresh token, set as cookies |
| `handle_refresh()` | Validate refresh token, rotate, issue new tokens, **detect theft** |
| `handle_logout()` | Revoke refresh token, clear cookies |

**Theft detection:** If a revoked refresh token is reused, ALL tokens for that user are revoked. The logic:
1. User A logs in → gets refresh token `T1`
2. Attacker copies `T1`
3. User A refreshes → `T1` is revoked, gets `T2`
4. Attacker tries `T1` → it's revoked → **all sessions nuked** → User A forced to re-login

```python
if token_record.is_revoked:
    # Someone reused a rotated token = possible theft
    await db.execute(
        update(RefreshToken)
        .where(RefreshToken.user_id == token_record.user_id, ...)
        .values(is_revoked=True)
    )
    raise HTTPException(401, "Refresh token reuse detected — all sessions revoked")
```

### `controllers/chat_controller.py`

| Function | What it does |
|----------|-------------|
| `create_conversation()` | Create a new conversation for the user |
| `list_conversations()` | Fetch all conversations, newest first |
| `get_conversation_messages()` | Get messages, verify ownership |
| `send_message()` | Save user message → call OpenAI → save assistant response |
| `delete_conversation()` | Delete conversation + cascade messages |

**Ownership checks:** Every function verifies `conversation.user_id == user.id`. User A can never see User B's conversations.

## Routers — The HTTP Layer

Routers are deliberately thin. They:
1. Parse HTTP-specific things (path params, cookies, request body)
2. Call the controller
3. Return an HTTP response

Example from `routers/auth.py`:

```python
@router.get("/google/callback")
async def google_callback(request: Request, db=Depends(get_db)):
    token = await oauth.google.authorize_access_token(request)  # HTTP concern
    userinfo = token.get("userinfo")                            # HTTP concern
    user = await handle_oauth_callback(...)                     # business logic
    response = RedirectResponse(url="/chat.html")               # HTTP concern
    await issue_tokens(user, response, db)                      # business logic
    return response
```

## Frontend — Static Files

### `static/index.html` (Landing page)

A single "Sign in with Google" button that links to `/auth/google/login`. No JavaScript OAuth SDK needed — it's just an `<a>` tag:

```html
<a href="/auth/google/login" class="oauth-btn google-btn">Sign in with Google</a>
```

### `static/js/auth.js` (Auth wrapper)

The key function: `authFetch()` — a wrapper around `fetch()` that handles token refresh:

```javascript
async function authFetch(url, options = {}) {
    let response = await fetch(url, options);
    if (response.status === 401) {
        // Try refreshing
        const refreshResp = await fetch('/auth/refresh', { method: 'POST' });
        if (refreshResp.ok) {
            response = await fetch(url, options);  // retry original
        } else {
            window.location.href = '/';  // refresh failed → login
        }
    }
    return response;
}
```

**Every API call in the app goes through `authFetch()`** instead of raw `fetch()`. This means token refresh is transparent to the rest of the frontend code.

### `static/js/chat.js` (Chat client)

Manages the chat UI: loading conversations, sending messages, displaying responses. Uses `authFetch()` for all API calls so auth is automatic.

## How the auth flow actually works end-to-end

```
1. User clicks "Sign in with Google" on index.html
   → <a href="/auth/google/login">

2. Router (auth.py) asks authlib to redirect to Google
   → 302 to accounts.google.com/o/oauth2/v2/auth?...

3. User approves on Google's consent screen
   → Google redirects to /auth/google/callback?code=...&state=...

4. Router (auth.py) receives the callback
   → authlib exchanges code for tokens (server-to-server)
   → authlib verifies the ID token signature using Google's public keys
   → Extracts email + sub from userinfo

5. Controller (auth_controller.py) handles account linking
   → Checks oauth_accounts for existing link
   → Checks users for matching email
   → Creates user + oauth_account if needed

6. Controller issues YOUR tokens
   → JWT access token (30 min) → httpOnly cookie
   → Refresh token → sha256 hash in DB, raw in httpOnly cookie

7. Router redirects to /chat.html
   → Cookies are set, user is authenticated

8. chat.js loads conversations via authFetch('/api/conversations')
   → Cookie sent automatically
   → Backend reads JWT from cookie → validates → returns data

9. 30 minutes later, JWT expires
   → authFetch sees 401 → calls POST /auth/refresh
   → Backend validates refresh token, rotates it, issues new JWT
   → Original request is retried → user never notices
```
